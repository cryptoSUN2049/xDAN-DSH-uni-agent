## 固定什么

候选清单：deployment/versions/first-gpu-candidate.json。固定集成代码、配对VERL、DSH发布物、Harbor、镜像digest、Python依赖锁、模型/Tokenizer、任务/数据划分、verifier、Harness、训练配置和随机种子。驱动及硬件记录实际版本，兼容检查通过后冻结部署组合。
null表示尚未恢复/确定，不能伪装成可部署锁文件。先形成候选，再用运行证据升级为已验证版本；首轮不追逐上游latest。

## 首轮顺序与验收

1. 环境：隔离安装；GPU推理/训练依赖、DSH runtime、网络与容器能力预检。不得覆盖已有作业。
2. 旧链路复建：DSH → Uni-Agent/Gateway → VERL，复用现有Qwen3-4B recipe；若用户用自有微调模型，另固定其revision并检查架构和Tokenizer，不静默替换。
3. 冻结小批任务，训练前在独立留出集评估；固定Harness、预算、解码、种子和verifier。
4. 少量真实更新：初始目标4个optimizer step（依有效rollout和资源调整）；必须有有限loss/gradient、有效奖励、真实token与回执、完整group准入和训练消费证据。
5. 对比加载前后可训练张量：数值delta非零且有限；LoRA模式比较adapter，不要求冻结base改变。文件hash只作辅助，不能单凭序列化文件变化证明训练。
6. 新进程独立reload指定checkpoint/adapter，核对加载身份与键；跑与训练前相同的留出任务。
7. 报告成功率、有效完成率、工具错误、token/时延和失败案例；少量样本不宣称统计显著提升。权重有变化但reload失败仍判工程失败；小幅指标波动记录，不把明显提分设为首轮门槛。
8. Harbor增量单独验收：先单任务Docker oracle，再DSH bridge执行、评分和纳入训练。旧链路通过不等于Harbor已通过；Harbor能力若被容器权限阻塞，明确分项状态。

## 分批冻结场景

| 批次 | 任务与目的 | 验收重点 |
| --- | --- | --- |
| A 工程 | 优先复用已有DSH可验证任务；先1—2类，使用独立训练/留出实例 | update、reload、评估与证据闭环 |
| B DSH专长 | 工具调用、调度、错误恢复、多步骤完成 | 同预算独立成功率与调用可靠性 |
| C 记忆与上下文 | 中断恢复、信息保留/检索、上下文压缩 | 跨阶段完成与信息准确性 |
| D 终端泛化 | Harbor固定任务版本，分离训练任务与正式benchmark | 留出泛化；不在测试集训练后报测试成绩 |
| E Harness RL / RSI | 技能发现/复用、受控候选改进与验证 | 分离模型权重提升与Harness改进，候选不自动发布 |

批次是验收边界而非禁止并行设计；RSI设计可提前，训练实现按基础能力依赖推进。
每批明确输入、工具权限、成功条件、预算、verifier、训练/验证/测试划分，再冻结版本。
第一轮只做A和Harbor最小增量；不混入全部能力，以便定位失败来源。
