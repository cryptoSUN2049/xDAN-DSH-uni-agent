# r4全零奖励：业务与记忆行为缺口，未发现该批评分错误

独立只读检查r4八步全部32个已准入B的真实产物，并检查selected-r1 WS05 A的重复读取。原始产物摘要、fixture哈希、独立评分和循环证据见 [JSON](work-state-r4-zero-reward-rootcause.json)。未运行GPU，未改回执、任务或评分；控制器参考仅用于诊断，没有注入模型或生成SFT数据。

## 直接原因

| 检查 | 实测 |
|---|---|
| 原回执与独立业务重评分一致 | 32/32 |
| 控制器合法参考产物可被同一评分器接受 | 32/32 |
| 两个结果文件存在 | 21/32 |
| 完整业务配置正确 | 0/32 |
| 计划执行合法 | 8/32 |
| B实际尝试view index | 1/32 |
| A传入B的memory为空 | 6/32 |

“两个文件存在”只是output_contract，不能替代JSON/业务正确。具体例子：WS06容量应由公开peak+reserve计算出125，真实B却写capacity100；WS01目标capacity118/168，B常写100及虚构`configure_capacity`、`action1`等动作。其它B缺少最终文件，或虽有占位memory却未读取和使用。全部配置错误使严格任务奖励为0，四个终态B同分导致GRPO优势和梯度为0；这与已核实的全零moment、LoRA B及4→8参数不变相符。

上述参考检查能排除“该批合法答案一律被拒”的错误，不能证明评分器绝无任何边界bug。未发现应当修评分以接受这些实际产物的理由；不能放宽类型、允许默认100、忽略多余字段或接受虚构动作迁就模型。

## 72次view并非不断被拒造成

selected-r1 WS05 A共72view+6create：六个memory路径各view11–12次，source只view2次。错误工具结果仅seq15/30/45/60/75/90，即第一次查看尚不存在的六个目的文件；create后反馈成功，后续仍重复成功view，最后原turn/end为max-tokens。

源只读限制没有要求模型反复读取，也没有阻止在允许目的地保存事实。当前提示虽说可选、给出停止条件，但仍展示六个可选文件，模型实际把它们变成了反复检查清单；这是行为与任务呈现的交互问题，不能将“六文件列表导致循环”当已证明的单一因果。另一次原token审计已证实index提示和首个工具结果进入B记录历史，不能继续用漏历史解释这一例不读index。

## 最短有价值的下一层学习路径

首先完成独立工程reload验收；本建议不阻塞工程、不要求中断全零训练，也不扩大成新trainer或SFT。

下一课程应独立命名并保留旧任务：先做一个短小的跨会话配置恢复任务。A读取含一个动态业务事实的权威源，只提供index与handoff两种可选目的地；B新会话收到清晰业务键/类型和固定入口，源事实仍只存在A，必须通过模型真正写出的文件获得。B实际写出一个正确配置及空业务计划；保留完整A/B采样、冻结、终态奖励、n4与安全准入。动态值与不需要记忆的对照任务分开设计，不能控制器自动填memory/index或把A源再偷偷给B。

先以同一固定基座和有限n4组测可达性，检查模型是否真实保存、B是否读取、产物是否合规；不只看文件个数。确认有真实成功/失败差异后，再递增为依赖计划、多源兼容、版本冲突及六文件自主组织。最小课程仍训练可复用的“保存后跨会话恢复业务事实”，而不是把所有难度同时叠加再期待二元奖励自发产生信号。

当前不优先改分解奖励：这32例连完整配置都没有正确，奖励文件存在、阅读次数、重复schema_version常量或无工作流的`[]`会掩盖实质失败。若未来需要部分业务奖励，必须另立版本，以非平凡动态事实/独立可执行业务子目标为依据，同步保留严格成功率与安全门；不能为制造方差调整原分数。
