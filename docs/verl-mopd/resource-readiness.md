# MiMo → MOPD 独立训练资源与真实验收准备

更新：2026-09-22。对应工作目录 `verl-mopd`、分支 `worktree-verl-mopd`。
设计入口：[mimo-objectives-design.md](mimo-objectives-design.md)。

## 结论与证据边界

**需要单独安排 MOPD 的 GPU 配额、任务执行配额、存储和预算。** 推荐先落实短期、可释放的 9B 工程验收资源，完成实际内存与吞吐测量，再决定能力实验和 27B 扩展的长期配置。这里的“单独”是明确分配和隔离；不要求永久购买服务器。

当前原生同步配置由学生训练/rollout 共享角色、SWE 教师角色、Terminal 教师角色组成。每个角色至少占一个 GPU 时，拓扑下限是 **3 个 GPU**。这是角色分配下限，**不是“三张卡一定装得下”的容量结论**。学生全参数训练、教师大小、上下文长度和 Top64 logits 开销可能要求更多 GPU 或经过验证的 offload。

本文件基于本会话已核实记录和仓库合同编写，未重新查询远端、未启动 GPU 任务、未预订资源、未授权费用。

| 项目 | 已知事实 | 对新任务的含义 |
|---|---|---|
| 原有节点 | 历史快照为 2×96GB GPU，GPU0 正在运行旧评测 | 不满足当前三角色独立部署；不能把空闲快照当作资源分配，也不能终止旧作业腾资源 |
| 当前 MOPD | CPU 数学/工程测试和本机真实任务准备已有证据；本轮尚无真实 GPU 训练闭环 | 不得将 CPU 成功写为 GPU 验收完成 |
| Modal 账单 | 会话最新已记录共享项目用量为 $864.40 / $900；此处未重查 | 属于旧任务预算，不能当作新 MOPD 预算；算术差额也不是可自动使用的授权 |
| 模型目录 | 9B、27B 基础模型存在；旧 merged 教师目录没有可用 safetensors 产物 | 基础模型存在不等于领域专家就绪；需要导出和真实加载验收 |
| 教师兼容性 | 9B 与 27B 基础词表相同，但 added-token ID 映射存在差异 | 跨型号直接蒸馏仍需逐项兼容核查；不能因此断言历史训练失败原因 |

## 一、显存估算：先算下限，再做 profile

以下只用名义参数量作算术估算，GB 为十进制；不是模型实测值，也没有计入激活、KV cache、临时张量、通信、碎片和运行时。实际以模型 tensor 清单、dtype、优化器和峰值测量为准。

| 对象 | 9B 名义参数 | 27B 名义参数 | 解释 |
|---|---:|---:|---|
| 冻结 BF16 权重 | 18 GB（约 16.8 GiB） | 54 GB（约 50.3 GiB） | 每个独立教师各有一份权重；仍需 KV cache 与评分工作区 |
| BF16 权重 + BF16 梯度 + FP32 Adam 两个状态 | 108 GB（约 100.6 GiB） | 324 GB（约 301.7 GiB） | 典型全参数训练状态的 12 bytes/参数示例；实际 optimizer 可能不同 |
| 上项再加 FP32 master weights | 144 GB（约 134.1 GiB） | 432 GB（约 402.3 GiB） | 16 bytes/参数示例；不能假定实际一定有或没有 master weights |

当前继承的工程配方已经是 LoRA rank=16、alpha=32、target_modules=all-linear，以上全参数估算不是当前启动器的实际开销。LoRA 工程验收也不能标记为全参数论文复现。

这意味着：即使一个 9B 冻结教师容易放进某张大显存卡，也不能推断同样大小的学生全参数训练能放进去。FSDP 分片、CPU optimizer offload、gradient checkpointing 和训练/rollout 权重切换分别影响峰值；必须记录实际启用项。改用 LoRA 会改变训练方法，不能为省资源而静默替换全参数方案。

### Top64 的特殊成本

- 教师传输的 Top64 候选与 logprob 约按有效位置数 × 64 增长。
- 学生仍须用**全词表**归一化概率。Top64 不代表学生只算 64 类 logits，也不代表显存与词表大小无关。
- 仅一个 `[S,V]` logits 张量的大小就为 `S × V × dtype_bytes`。示例：S=8192、V=250000 时，BF16 约 4.10 GB，FP32 约 8.19 GB；这只是示意，V 不是已核实的本模型词表大小，S 应取实际同时处理的位置数。
- FP32 分块 logsumexp 能避免额外完整 log-softmax 张量，但基础 logits、反向图与其他激活仍有成本。必须测 forward、backward 和 optimizer step 各阶段峰值。
- 首轮 Top64 支持范围是 FSDP、TP=1、序列并行=1、关闭 fused kernels。不能为了塞进设备而直接改成未经支持的 TP/SP 后端。

## 二、9B 工程验收资源合同

首次运行前将以下项目填入运行台账和冻结后的 run contract。未完成的项目是准备缺口，不是已发生的失败。

- [ ] **资源归属：** 节点、GPU UUID、独占时间窗、唯一操作者、运行锁；旧训练与旧评测保持原分配。
- [ ] **角色布局：** 学生训练/rollout、SWE 教师、Terminal 教师的具体 GPU 集合；满足原生 placement group，角色不能靠逻辑名称重复占用同一张卡。
- [ ] **容量方案：** 明确学生是否全参数、FSDP world size、optimizer dtype/offload、activation checkpointing；声明教师大小与副本数。先 profile，才能承诺上下文和并发。
- [ ] **主机与磁盘：** RAM 足够容纳 offload/模型加载峰值，磁盘覆盖模型、HF 导出中间产物、至少连续两个完整 checkpoint、rollout 证据和临时文件；用真实文件大小算容量并留余量。
- [ ] **软件合同：** 项目 commit、VERL 固定 revision、补丁摘要、CUDA/PyTorch/vLLM 等实际版本、驱动与所选 GPU 的兼容验证；CPU 测试环境不冒充 GPU 环境。
- [ ] **任务执行配额：** Harbor/Modal 环境独立 run 标识、并发上限、超时和清理责任；训练 GPU 与沙箱 CPU/存储费用分别核算。
- [ ] **独立预算：** 资源单价凭据、预计租用时长、GPU 与沙箱分别的费用上限、计费起止、主动释放责任；当前 launcher 的预算记录不是美元硬上限。
- [ ] **模型身份：** 两个教师和学生的文件摘要、实际 worker 加载证明、tokenizer/template 兼容检查、固定样例评分；配置中的路径不是加载成功证据。
- [ ] **数据合同：** 在目标节点重新生成 parquet 路径并验证任务/文件 fingerprint；训练、工程验证和能力测试明确区分。
- [ ] **验收证据位置：** 统一保存配置、路由、采样概率、teacher payload、mask、实际反向更新、checkpoint、恢复游标和费用记录。

资源准备优先采用支持这份合同的短期独立分配。复用现有节点可以成为后续方案，但需要旧任务结束、明确重新分配，并调整拓扑后重新验收，不能让代码悄悄共享教师进程来绕过资源缺口。

## 三、教师资产：能加载与能教是两层验收

1. **HF 导出与加载。** 现有 OPD/RL 的 FSDP checkpoint 与 optimizer 文件不是可直接使用的 HF 教师。应从完整 checkpoint 导出到新的独立目录，验证权重 shard/index、模型 config、tokenizer/template，再由实际 teacher worker 加载并评分。未完成导出不能写“教师已就绪”。
2. **工程路由。** 可用两个有明确不同身份的可加载模型验证领域路由和 loss 接线；这只证明多教师工程链路。若使用相同基础权重作为占位，必须明确标注无法凭相同数值证明路由正确，需要其他身份与故障注入证据。
3. **专家资格。** 同一个 RL run 的早晚 checkpoint 不自动构成两个互补领域专家。每个教师要在对应独立评测领域优于同源学生基线，并检查其他领域的退化。具体统计精度与题量另行设计。
4. **论文复现边界。** 优先从同源 SFT 初始化得到领域教师，再整合到同源学生，可减少 tokenizer 和模板变量；如做 27B→9B 跨尺度蒸馏，应独立命名并额外验收兼容性，不将其混为同源 MOPD 的唯一检验。

## 四、分阶段部署与真实验收

### R0：本机与资源准备

完成算法参考值/梯度、mask、归约、原生接线、错误输入、恢复合同测试；准备资源合同与教师导出。这里不产生 GPU 训练结论。

现有数据为 4 条 train、2 条工程 validation，来源和历史 nop/oracle 已核对。历史验证未在本轮重跑，且 validation 来自历史训练池；适合工程 smoke，不适合宣称泛化提升。

### R1：在实际设备上定容

先完成单模型加载与教师实际评分，再测学生训练的 forward/backward/step；随后测三角色同时驻留、训练与 rollout 切换和 Top64。

记录 GPU 峰值 allocated/reserved、进程显存、CPU RAM、数据传输、teacher prefill tokens/s、学生更新耗时和 checkpoint 体积。由短轨迹逐步提高到合同内上下文长度和并发，每次只调整容量变量。缩小工程任务用于排查可以接受，但不能把缩小后的通过称为完整上下文验收。

### R2：完整工程闭环

各配方分别从冻结初始化运行：PG sequence → Top64 reverse → Flash ORM/IS。每个配方至少验证：

`真实任务 rollout → 正确领域教师评分 → 非空有效 mask → 真实反向和参数变化 → 保存 → 新进程重载 → 恢复到下一批 → 再次更新 → 清理资源`。

同步检查两个领域实际被路由到对应教师、Flash 的真实 sampling logprob 和 N≥2 分组、Top64 全词表归一化、长短轨迹归约、无重复更新。exit 0、一个 checkpoint 或一个成功任务都不能单独算闭环通过。

### R3：能力验证

重新准备独立 held-out 集，固定初始化、任务、采样设置和更新预算，分别比较基线/PG sequence/Top64/Flash。报告分领域成功率、配对差值及不确定性、长度/工具轮次/截断、遗忘、每次成功成本。小样本只提供方向性证据，不足时明确写不确定。

序列平均修正长度权重，不保证 thinking 变短。长输出与性能波动触发诊断和人工复核，不新增任意自动取消规则；明确授权的预算与时间窗、资源冲突和无效数值另按执行合同处理。

### R4：27B 扩展

9B 的代码与工程闭环成立后，27B 重新做 R1 定容，不按参数比例直接承诺卡数或吞吐。27B 全参数学生的 optimizer 状态、Top64 全词表激活、教师大小和并发决定容量；增加 FSDP 分片或 CPU offload 也需测试通信与恢复。

27B 的 GPU 数量、单卡显存、RAM/磁盘、上下文上限和预算均待 profile 后冻结。若要扩大到新并行后端，先实现并验证该后端，再计算训练资源，而不是租完资源后静默更换目标。

## 五、尚缺的信息

- 可明确分配的新 GPU/节点或原节点后续排期；其容量和软件兼容信息。
- 本轮独立 GPU 与任务沙箱预算、计费方式和授权时间窗。
- 两个领域专家的完整 checkpoint、可加载 HF 导出、实际评分证明及专家资格。
- 9B 首轮全参数/offload/分片的实测峰值与上下文、并发合同。
- 能力评估的独立题池、配对评估设计以及 27B 的独立资源测量。

这些缺口不阻止推进已批准的代码和 CPU 验证；它们阻止把“准备好了”写成“真实训练与能力验收已完成”。
