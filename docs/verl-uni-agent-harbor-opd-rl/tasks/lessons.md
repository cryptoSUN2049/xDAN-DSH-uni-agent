# Lessons：verl-uni-agent-harbor-opd-rl

1. **venv 不能建在 pod 本地盘。** 2026-09-16 发现之前通过 GPU 组件验证的 venv 在 `/tmp`，pod 重建后全丢，只剩 freeze 和 cache。规则：venv / cache / 模型 / 证据只放 `/workspace`，脚本层面拒绝其他路径（`uv-lane-bootstrap.sh`）。
2. **每个 GPU lane 的 freeze 必须进仓库。** 远端 `runs/` 里的 freeze 是唯一幸存物，如果它也在本地盘就全没了。规则：每次改依赖后 `uv pip freeze` 覆盖 `deployment/versions/uv-lanes/<lane>.freeze.txt` 并同提交。
3. **SSH 端口随 pod 重建变化。** 12524 → 30284。规则：handoff 里写端口时标注日期，冷启动第一步先核。
4. **交接文档放 `docs/<worktree>/tasks/`，不放根目录 `tasks/`。** 旧位置的 handoff/notes/memory 已 git mv 过来。
5. **跨项目的运维办法要"继承"而不是"引用"。** 用户明确要求把 MetaRSI 的 uv 管理办法搬到本项目并按本项目路径落地，链接过去不算完成。
6. **DSH 专属校验不能带进 Harbor 路线。** `require_verifier_reward` 只有 `uni_agent/tasks/dsh` 会填 `TaskResult.verifier_reward`；Harbor adapter 只给 `reward` + `eval_completed`（`finished=None`）。带着它训练会让每个 session 失败并被 sync refill 反复重采，看起来像"卡住"。规则：从 DSH 脚本派生新 recipe 时逐条核对 `require_*` 与 postprocessor 是否依赖 DSH 字段；`mask_unfinished_episode` 只作用于 `finished is False`，None 不受影响。
7. **远端 `pgrep -f`/`kill` 会命中自己的 ssh shell。** 用 `pgrep -f <script名>` 杀进程时，承载该命令的 `bash -c` 自身也匹配，ssh 直接 255 断开。规则：用 `ps -eo pid,cmd | grep -E "^ *[0-9]+ [^ ]*python -m verl\.trainer\.main_ppo"` 这类锚定到可执行文件的模式；`pgrep -f "main_ppo"` 连存活检查都会误判（第二次踩：r2 已退出仍报 alive）。
8. **DAPO 依赖 reward 方差。** `filter_groups` 会把组内 reward 全相同的 group 扔掉重采。（2026-09-17 更正：VERL V1 的 ReplayBuffer 忽略 `max_num_gen_batches`，不会"耗尽后报错"，而是循环数据集一直补采，见第 29 条。）先用 GRPO 拿到 0/1 混合再开 `DAPO=1`。
9. **VERL 训练结束后主进程可能挂在 wandb teardown。** r2 的 step、checkpoint、wandb 同步全部完成后，`wandb` atexit 抛 BrokenPipe，主进程不退出、`exit-code` 不写。规则：判定完成看 `global_step_N` 目录 + step 指标行 + wandb "View run"，不等 exit-code；起下一轮前按上一条的模式核进程再清理。
10. **Modal 消费上限是训练链路的硬依赖。** 一天内 oracle + rollout + 三轮训练约 80 个沙箱就触到了 workspace spend limit，表现为 `ResourceExhaustedError` → 每条 trial `Sandbox not found` → `fail_on_rollout_error` 终止。规则：起长训练前先在 Modal 控制台核余额/上限；acceptance 的 failure_reasons 里出现 `spend limit` 直接判外部阻塞，不重试。
11. **`ruff … | tail -1` 会吞掉退出码。** 用管道时 `&&` 判断的是 `tail` 的退出码，lint 失败照样 commit/push（f9e1fca 就这样漏过去了）。规则：门禁命令不接管道，或用 `set -o pipefail`；`ruff check .` 直接跑，不截断输出。
12. **Harbor 的 `--agent-timeout` 不覆盖卡在 Modal API 的沙箱调用。** attempt4 一条 fix-git trial 在 terminus-2 上下文摘要后卡在 Modal 调用 30+ 分钟（进程只连着 Modal 443，vLLM 空闲），整步被拖住。规则：Harbor task config 必设 `trial_timeout_sec`（适配器 `run_harbor_cli` 用 `asyncio.wait_for` 兜底，超时 exit 124）；训练脚本默认 `FAIL_ON_ROLLOUT_ERROR=0`，让 `sync_refill_failed_groups` 补组而不是中断整步；`modal container stop` 在非交互 shell 要加 `-y`。
13. **VERL v1 checkpoint 布局是 `global_step_N/actor/*.pt` + `data.pt`**（sync 旧布局把 .pt 直接放在 `global_step_N/`）。校验和 delta 都要兼容两种布局；attempt5 训练成功却被误判 "checkpoint missing" 白等一轮。
14. **`set -e -o pipefail` 下，grep/find 无匹配会让 `x=$(...)` 直接退出脚本，且没有任何输出。** `trainer_pids`、`find_final_ckpt` 两处都因此静默失败。规则：辅助函数里 `grep … || true`、`find` 前先 `[[ -d ]]`；阶段脚本失败时若 driver.log 没有本阶段任何行，先怀疑这一类。
15. **两个 pod 共享一个 `/workspace` 时，data 阶段会重建 `data/stage1/tasks-*`，可能打断另一 pod 正在启动的 trial。** 第二台机器起 pipeline 时用 `SKIP_STAGES=data`（沿用已 PASSED 的 parquet）或独立 `DATA_DIR`；`rsync --delete` 源码也只做一次。
16. **Mac 断网 → 两台 pod 的 Ray 同时收到 SIGTERM（2026-09-17 02:48/02:50）。** 用 `nohup … &` 从 ssh 命令里起的驱动仍和会话有隶属关系。规则：远端长任务一律 `examples/harbor_opd_rl/launch-detached.sh`（setsid + nohup + /dev/null，trap 记录信号），"训练完接评测"用服务器端 `;`/`&&` 链，不在 Mac 上挂等待。
17. **共享卷配额（500 GB）被 22 个 8.7 GB checkpoint 撑满，`Disk quota exceeded`。** 每条 run 只留首尾 checkpoint；清理前先核对哪个 checkpoint 可能损坏（保存中被杀的 `global_step_N` 会 `EOFError`），别把它前一个删了——pipe-r3 的 step 6 损坏、step 5 已删，只能重训。配额已加到 1 TB。
18. **checkpoint 保存后、指标上报前被杀 → 有 checkpoint 无指标。** 复用逻辑改为：控制台缺失则从 wandb 重建；仍缺最后一步时接受但写 `reuse-note.txt`。
19. **评测比训练更吃 Modal 额度。** 89 题 × n 次 = 每次基线 89–267 个沙箱，加上镜像构建也计费；两次基线把当天额度打穿，连带训练链被迫暂停。规则：基线评测先 n=1；起评测前用探针沙箱核额度；额度按"训练每步 batch×n + 评测题数×n"预估并留 50% 余量。`ImageBuildError: terminated due to external shut-down` 与 `NotFoundError/ConflictError` 成片出现都是额度耗尽的表现，不是任务本身的问题。
20. **共享卷上的 `pipeline-summary.jsonl` 可能出现 NUL 填充的撕裂行。** pod 断电/重建时正在 append 的一行被写成一串 `\0` 再接 JSON，`json.loads` 直接失败，summary/acceptance 整阶段 FAIL（pipe-r2 07:36）。规则：读 jsonl 证据一律去 NUL、跳空行；写证据的 `record` 保持单次 `printf`。
21. **验收要以记录为准，不以环境变量为准。** 重跑 `FROM_STAGE=acceptance` 时没带 `TRAIN_STEPS`，脚本用默认值算 `resume_continued` 得出 FAIL；同时控制台解析把非指标行记成 `{}`，让 `all_finite` 与 wandb 对账假失败。规则：验收从 train 记录里取实际步数；解析器丢弃没有 `training/global_step` 的行；假 FAIL 与真 FAIL 要在脚本里分清。
22. **Modal 的 spend limit 是"账期上限"设置，不是余额。** 报错原文 `Container terminated due to reaching billing cycle spend limit` / `Workspace … has exceeded its spend limit`：加 $10 后 2.5 小时内（pipe-r3 6 步 + resume + 89 题基线）第三次触顶。规则：训练前让用户在 Modal 工作区设置里把 spend limit 调到覆盖整个计划（每步 batch×n 个沙箱 + 评测题数×n，留 50% 余量）；链路上一律用 `deployment/bootstrap/modal-quota-wait.sh && …` 排队，额度恢复自动续跑，不靠人盯。
23. **resume 阶段曾经继承的是"启动时的环境变量"，不是训练时的参数。** 2026-09-17 10:45 额度恢复后自动续跑的 pipe-r3 resume 没带 `TRAIN_MAX_SAMPLES/VAL_MAX_SAMPLES`，训练集退回默认 4 题、held-out 1 题，与原训练（20/5）不一致，只能停掉重跑。规则：`40_train.sh` 把所有影响训练的参数冻结到 `train/stage-env.sh`，`60_resume.sh` 先 source 它（提交 1ec1b22）；手工续跑链只需 `PIPE_ROOT` + `FROM_STAGE`。
24. **按命令行模式杀进程，第二次命中了自己的 ssh shell。** `ps | grep -E "^ *[0-9]+ (bash) .*detached-"` 匹配到了承载这条命令的 `bash -c`（命令文本里就含这个模式），ssh 直接 255 断开，目标进程一个没杀。规则：先用只读命令列出 PID，下一条命令只 `kill <明确 PID>`；杀进程的命令里不出现目标模式。
25. **OPD 的 Teacher/Student 必须同词表。** Qwen3-4B `vocab_size=151936`，Qwen3.5-9B 与 Qwen3.8-27B 都是 `248320`（`Qwen3_5ForConditionalGeneration`）。4B 不能蒸馏 27B，27B Teacher 只能配 9B Student。规则：选 Teacher 前比对 `config.json` 的 `vocab_size` 与 tokenizer 哈希（`runs/tokenizer-4b-9b-preflight.json` 是现成模板）。
26. **Qwen3.5 训练依赖 `flash-linear-attention`，推理不依赖。** vLLM 自带 fla 算子，所以 9B/27B 能推理不代表能训练；transformers 缺 fla 会退回纯 torch 的 gated delta rule，慢且在 `use_remove_padding` 打包序列下无法按序列边界重置状态。规则：换架构先做依赖预检（`fla`、`causal_conv1d`、`flash_attn` 的 import），缺的装进 lane 并更新 freeze（ecbde4b 加了 fla 0.5.2；causal_conv1d / flash_attn 有 torch 回退，暂缓）。
27. **数据源首次入训前必须过 oracle 闸门，闸门确实拦住了问题。** `STAGE1_SLICE=0` 把 swe-rebench-v2-fv 21 题混进来，按目录名排序它们排在最前，oracle 用参考解跑 2 题都报 `RewardFileNotFoundError`：verifier 调 `pytest --ctrf`，任务镜像里的 pytest 不认这个参数，没有 CTRF 报告就不写 reward。若跳过 oracle 直接训练，这一半题目会全部 0 分并反复触发 DAPO 重采、白烧 Modal。**根因（子代理排查 + 复验）**：25/25 道 swe-rebench 的 `task.toml` 写了 `docker_image`，值等于 Dockerfile 的 `FROM`；Harbor 0.16.1 有 `docker_image` 且 `force_build=false` 就直接拉该镜像、不构建 Dockerfile，而 `pytest-json-ctrf` 只在 Dockerfile 里装。修复 5fa9d6a：数据阶段在 `docker_image` 等于 `FROM` 时删掉它；复验 oracle 3/3 reward 1.0（`docs/…/swe-ctrf-fix/`）。与 Terminal-Lego 镜像别名是同一类问题：**只要 Dockerfile 在 `docker_image` 之上加了层，就必须让 Harbor 构建 Dockerfile。**规则：新数据源不 `SKIP_STAGES=oracle`；共享 pod 的第二条链先确认它的数据口径也过了闸门。
28. **Modal 换 key = 换工作区，续跑链会自动接上。** 2026-09-17 旧 profile `shootime007` 触发 billing cycle spend limit，用户给了新工作区 profile `l98348740`。在 pod 上 `modal token set … --profile=l98348740` + `modal profile activate` 后，`modal-quota-wait.sh` 每次探测都重读 `~/.modal.toml`，下一次探测即放行。本机第一次 `modal token set` 报 "Could not connect to the Modal server"，重试即成功，不是 key 的问题。注意：新工作区镜像缓存是冷的，首批 trial 会重新构建镜像。
29. **V1 下的 DAPO 是逐批补采，代价是步长翻倍。** pipe-r5 训练日志：`algorithm.filter_groups.max_num_gen_batches=10 is ignored by the built-in V1 ReplayBuffer; use max_inflight_gen_batches`。开了 filter 后 `gen_batch_size=1`、默认 `max_inflight_gen_batches=1`，同时只有 `train_batch_size` 道题在跑，组内无方差就丢弃再补；数据集会循环，没有总次数上限。按 pipe-r2 的 45% 无方差组估算，每步墙钟与沙箱数都接近 2 倍。规则：先用 GRPO 拿基准曲线；要开 DAPO 时同时调 `DAPO_MAX_INFLIGHT`（脚本已改为接这个参数）。
30. **GPU 利用率长期 0% 说明瓶颈在沙箱，不在显卡，应放开并发。** 每步墙钟由最慢的一条 agent 轨迹决定，把 `TRAIN_BATCH_SIZE` 2 → 4、`CONCURRENCY` 16 → 32，每步时间基本不变而轨迹数翻倍。约束是 Modal 额度（与 Tinker 线共用 spend limit，放开前先打招呼）和 vLLM KV 容量（超出只会排队，不会 OOM）。
31. **共享卷上正在被 bash 执行的脚本不能覆盖。** bash 边执行边按偏移读脚本；`scp` 覆盖同一文件后，等待中的 bash 回来会从旧偏移读新内容。`40_train.sh`、`60_resume.sh`、`run_tb21_pipeline.sh` 在 run 进行中都处于这种状态；最后一行是 `exec` 的训练脚本、以及被 `source` 一次读完的 `common.sh` 不受影响。规则：同步源码前先确认没有 run 正在执行目标脚本，否则等阶段结束或走 `sync-source.sh` 的空闲切换。
32. **沙箱失败被当成 0 分训练，是比"改坏代码没被罚"更严重的信号污染。** 子代理顺着代码查到：Harbor trial 只要没完成就记 reward 0，链路上没有任何地方读 `eval_completed`，所以镜像构建失败、Modal 资源不存在、额度耗尽、CLI 超时，都会让一条可能很好的轨迹拿到组内最负的 advantage（8 条里 1 条为 0 时约 −2.5）。历史上 63 次未完成的 trial 中有 57 次是基础设施故障。反过来，pipe-r6 里 3 次 `RewardFileNotFoundError` 全是模型把仓库改出 SyntaxError，swe-rebench 的 run_tests.py 却判成 infra。规则：未完成的 trial 必须分类（f81ae2c）。agent 超时、输出超长、verifier 最后一个 traceback 帧落在工作区内的，记 0 分；其余抛 `HarborInfraFailure`，框架只剔除这一条会话。改动 Python 适配器要等在跑的 run 结束后再部署，因为 Ray 会中途拉起新的 worker，新 worker 会导入新代码，同一个 run 里就会混用两种计分规则。
33. **Qwen3.5-9B 的推理引擎在每步 36864 个 token 时 OOM。** pipe-r4 第一次训练，13:41 在评 held-out 时，9B 的 vLLM 进程一次申请 26.84 GiB，而进程已经占了 89 GB，远超 `gpu_memory_utilization=0.45` 给它的预算。原因是脚本把 `max_num_batched_tokens` 设成整段上下文长度，混合线性注意力模型配 24.8 万词表时，激活显存超出了 vLLM 启动时的预估。27B Teacher 按同样的上限算 prompt logprobs 也会 OOM。规则：Qwen3.5 系列和 27B Teacher 一律设 `ROLLOUT_MAX_NUM_BATCHED_TOKENS=8192`、`TEACHER_MAX_NUM_BATCHED_TOKENS=8192`（cb73a63）。换模型时这个参数和显存比例要一起检查。
34. **数据顺序被预处理悄悄重排了。** Harbor 预处理器按目录名排序，而 `data.shuffle=False`，结果每个 epoch 都是先连续跑完 swe-rebench-v2-fv，再跑 terminal-lego-15k。pipe-r6 第 1 到 5 步全是 SWE 题，第 1 步因为新工作区要冷构建大镜像，耗时约 30 分钟。这类 run 的曲线会随题目来源周期起伏，"后几步对比前几步"的判据因此失效，只能比较不同 epoch 里同一来源的那几步。规则：按来源限额选题时给目录加序号前缀，保持交错顺序（9d6a11d，已实测是 TSTS…）。以后的 run 要么这样做，要么打开 shuffle。
35. **Qwen3.5-9B 的 vLLM 引擎在生成过程中显存持续增长，压低单批 token 数不能根治。** pipe-r4 第二次训练已经把单批上限降到 8192，14:41 评 held-out 时又 OOM：引擎进程占 91 GiB，申请的 7.25 GiB 正好是 8192 个 token × 24.8 万词表的 float32 logits。按进程查看，训练模型只占 19 GB，重启后的引擎是 45 GB（在 0.40–0.45 的预算内），说明是生成过程中从 45 涨到了 91。开启 prefix caching 时，vLLM 会给 Qwen3.5 自动启用实验性的 mamba "align" 缓存模式，4B 从未出现过这种增长，这是首要嫌疑，但**尚未证实**。规则：新架构先用保守的引擎设置跑通（prefix caching 关、单批 4096、显存比例 0.40），再逐项放开并观察引擎进程显存（`nvidia-smi --query-compute-apps`）。对照组必须同步改配置，否则对比失去意义。
36. **回复语言必须一直是中文，包括简短的通知确认。** 2026-09-17 夜里监听事件密集时，连续几条回复写成了英文，用户纠正"中文回复"。规则：不管是长汇报还是一两句的事件确认，面向用户的文字一律用中文；专业术语、命令、文件名可以保留英文。
