# pipe-r9 发现：SWE 的部分分奖励有"什么都不做"的高下限

日期：2026-09-18 05:40 UTC，pipe-r9 第 3 步后。脚本：`reward_floor_audit.py`（下限与分类）、`resolve_by_step.py`（按步按来源的解决率），均在 pod 上对 `runs/pipe-r9` 只读运行。

## 结论

pipe-r9 用 `HARBOR_REWARD_MODE=pass_ratio`：没解决时奖励 = 判分报告里通过的测试 / 全部测试。SWE-rebench 的测试包含 `pass_to_pass`（修复前就通过的回归测试），所以什么都不改也能拿到 `|P2P| / (|F2P| + |P2P|)`。

| 项目 | 数值 |
|---|---|
| SWE 训练题"什么都不做"下限，p10 / p50 / p90 | 0.5 / 0.936 / 0.987 |
| 下限 ≥ 0.9 的 SWE 训练题 | 50 道中 30 道 |
| 下限为 0 的 SWE 训练题 | 4 道 |
| SWE 验证题下限 | 0.954、0.984、0.981、0.977 |
| 训练前验证：SWE 解决 / 平均奖励 | 0/4 / 0.954 |

本轮前 3 步的 SWE trial（120 份判分报告中的 SWE 部分）：

| 类别 | 条数 |
|---|---|
| 解决 | 26 |
| 停在下限（等同什么都没做） | 9 |
| 低于下限（改坏了原有测试） | 22 |
| 高于下限（部分修复） | 1 |

另有 34 份判分报告的测试数与 expected.json 的 F2P + P2P 数不一致（参数化测试等），这些条目的分类是近似值，不影响结论方向。

## 影响

- 在没人解决的组里，GRPO 奖励的是"少改代码、别改坏"，而不是解题进展。只有 1 条 trial 真正拿到了部分修复的额外分。
- `critic/score/mean` 与验证分被下限抬高：第 2 步平均分 0.975，但 SWE 解决率只有 0.45；训练前验证分 0.924 几乎全是下限。
- 有人解决的组里方向仍然正确（1.0 对约 0.9，组内标准化后放大），所以本轮不是完全无效，但 SWE 的学习信号被污染。
- Teacher 蒸馏损失不受奖励影响。

## 处理

- 默认奖励模式改为 `binary`（`stages/common.sh`、`run_opd_round.sh`）。未部署到 pod，pipe-r9 按原配置跑完或由用户决定是否停止重开。
- 二值奖励下，本切片的解决率足够提供信号：前 3 步 SWE 约 45%、Terminal-Lego 约 69%。
- 若以后需要稠密信号，只按 `fail_to_pass` 计部分分，并要求 `pass_to_pass` 全过；不要把回归测试算进分母。
