VERL + Uni-Agent 训练系统：完整方案与执行入口

本页是当前 worktree 的唯一训练入口。版本：v2｜更新：2026-09-23｜范围：训练、观测、验证、止损、评测和证据归档。状态：设计已形成，控制面尚未实现，未启动新训练。

目标是把一次训练变成可复现、可比较、可停止、可审计的实验，而不是只确认“产生了 checkpoint”。

目标架构流程合同门禁补齐专项推进执行方案证据

1. 目标与当前判断

执行链已具备环境、数据、rollout、VERL 更新、checkpoint、独立评测和 W&B。
控制面缺失验证结果、有效 RL 组、行为预算、基础设施失败没有进入统一决策。
重训原则先 preflight 和 control-only，再正式训练；任何关键证据缺失都暂停。

现有 S2 证明了链路能运行，但不能证明 OPD→RL 带来能力提升：固定验证已经写入 W&B，却没有被标准报告和止损器消费；短组和 infrastructure failure 也没有与任务失败分开。

2. 系统架构

Run manifest→训练状态机→VERL V1 / FSDP LoRA→vLLM rollout→Uni-Agent Gateway→Harbor / Modal / Verifier→TransferQueue + update
train.log / trajectory / receipt+W&B history+validation JSONL+cost evidence→观测汇聚器→继续 / 暂停 / 回退

原则：同一个 run_id / step / group_uid / sample_id / rollout_id / policy_version / checkpoint_id 必须贯穿 rollout、verifier、update、validation 和报告。

当前两卡资源结论

SSH 节点实测为 2 × RTX PRO 6000 Blackwell，约 96 GiB/卡。纯 RL（9B）可行：一张卡训练，另一张卡评测或备用。9B + 27B OPD 也可行，但必须 student/teacher 分卡，先做 teacher 单题 logprob probe，并降低 teacher 的显存比例与 token batch。若实际是 48 GiB RTX 6000，正式 OPD 不作为默认方案，先走纯 RL；不能通过虚报 Ray GPU 数解决显存问题。当前 GPU0 仍有旧评测进程占用，重训前必须完成归属确认和交接。

3. 一次严谨训练的生命周期

  1. 冻结 manifest：commit、依赖、模型/tokenizer hash、数据 hash、任务 ID、预算、拓扑、W&B run。
  2. Preflight：GPU、CUDA/NCCL、vLLM、Gateway、Harbor、Modal 额度、W&B 写入和磁盘空间逐项验证。
  3. 固定基线：base 在 step-validation 和 development holdout 上独立评测；sealed 留到最终候选确定后。
  4. Control-only：2–4 步小跑，验证指标、短组分类、停止器和 checkpoint reload，不改变正式参数。
  5. 正式训练：每步先记录 rollout，再执行准入、update、checkpoint 和 step validation。
  6. 门禁决策：质量、有效组、行为预算、基础设施、数值稳定性、成本六类指标共同决定继续或暂停。
  7. 候选选择：只按 development holdout 选择 best checkpoint，禁止按训练 reward 选最优。
  8. 独立 reload：新进程加载候选，重新跑固定集，确认 checkpoint 可用且结果可复现。
  9. 最终评测：base / OPD / RL / hybrid 使用相同工具、任务版本、采样次数和预算。
  10. 归档：生成 manifest、summary、paired diff、behavior、cost、stop reason 和静态报告。

4. 观测与数据合同

维度必须记录判定用途
能力固定集 mean@4、任务级 paired diff、CI、完整性选择 best、检测回退
有效 RLexpected/valid group size、mixed group、reward distinct、non-zero advantage、补采判断是否真的有学习信号
行为预算prompt/completion tokens、turns、tool calls、max-turn、timeout、wall time检测“更贵但更差”
基础设施infra/task failure、verifier timeout、缺失 receipt、staleness、队列积压拒绝污染 batch
系统与成本GPU 利用率、throughput、sandbox 数、GPU/Modal 成本止损与复盘

所有字段同时写本地 metrics.jsonl、W&B 和最终 JSON；缺失、未计算、零值必须有不同状态，不能把验证失败写成 0 分。

5. 自动门禁与止损

门默认规则动作
质量小验证集回退先预警；按预注册规则做独立确认，确认后暂停暂停，保留 best
学习信号effective group fraction 连续两步低于阈值，或 reward 无方差暂停并换题/补采/调整 n
准入健康infra failure、短组、receipt 缺失超过阈值拒绝 batch；连续超阈值暂停
行为预算token、turn、timeout 或单步 wall time 超 run cap停止新 rollout并保存现场
数值NaN、非有限梯度、KL/prob diff 尖峰立即停止

每次动作写出 machine-readable stop_reason.json，并在 W&B 写入 control/decision、阈值和证据 URI。

7. 专项推进顺序

P0｜证据闭环

扩展 wandb_pull.py 与 report.py；统一 key、step、valid/missing reason；离线重建现有 S2。

P1｜控制器

只读观测器 + policy engine；每个 checkpoint 调用；暂停优雅退出并保存现场。

P2｜训练合同

failure taxonomy、短组补采、有效组指标、policy version 与 checkpoint identity。

P3｜观测平台

复用现有 rl-insight，接入 step/group/verifier/budget/checkpoint；补 W&B 五类面板。

P4｜评测矩阵

固定 base / OPD / RL / hybrid，统一 TB2.1、SWE-bench Verified 的工具与预算。

执行原则：先 P0，再 P1；P0/P1 通过小规模真实验证后，才启动长周期正式训练。

8. 可参考执行方案

启动前

  1. 创建唯一 run_id 和 manifest，冻结代码、数据、模型、依赖、阈值与 W&B。
  2. 执行环境、额度、GPU、Gateway、Modal、W&B、固定验证集 preflight；任一失败不启动。
  3. 运行 control-only 2–4 步并执行 reload + fixed validation；记录成本和完整性。

训练中

  1. 每步保存 raw rollout、准入清单、组统计、metrics、checkpoint 和 validation。
  2. 每步由控制器输出 CONTINUE、PAUSE 或 ROLLBACK，不允许人工凭单条日志判断。
  3. 超过阈值立即停新 rollout，保留进程日志、W&B、receipt 和 stop reason。

训练后

  1. 按 development holdout 选候选；独立进程 reload；再跑 sealed benchmark。
  2. 对 base/OPD/RL/hybrid 做相同配置的全量 paired evaluation。
  3. 归档到 docs/verl-uni-agent-harbor-opd-rl/<run-name>/，更新 handoff 和 lessons。

首轮从 base 做纯 RL：2–4 步机制验证，再有界试训正式长跑需 P0/P1 通过单卡/双卡按 manifest 固定
