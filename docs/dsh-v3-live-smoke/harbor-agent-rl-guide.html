01 / 建立分工

Harbor 提供可反复练习、验收的任务世界

先看全局：Uni-Agent 整体方案与 Modal / Harbor 接入设计。本页侧重概念、教程与开源调研。

可以把整个系统想成一所职业学校：模型是学生的“大脑”，Agent 是工作的方式，Harbor 组织实训场地和考试，VERL 根据成绩更新模型。

Harbor 把任务描述、工具环境、验收程序和运行记录组织在一起，让不同 Agent 在相同条件下完成任务。它可以服务评测、训练数据生成和强化学习；模型权重的梯度更新由训练框架承担。[Harbor 官方概览]

角色通俗解释本项目对应
模型 / Policy根据当前信息决定下一步说什么、做什么。Qwen3-4B；RL 主要更新其可训练参数。
Agent / Harness把模型、工具、记忆、循环和停止规则组织成能工作的程序。DSH Agent；决定如何调用模型和执行工具。
Harbor准备可执行任务与环境，运行 Agent，调用验收程序，收集产物和成绩。拟作为标准任务、环境与验收层接入。
Uni-Agent / Gateway协调 Agent 执行与模型服务，采集训练所需的请求和轨迹。现有接入骨架；还有 token、session 与 TransferQueue 证据链。
VERL根据轨迹和奖励计算训练信号，更新模型，再提供新模型继续尝试。现有 RL 训练后端。

你截图中的 Harbor Hub，是“可执行任务包”的分发目录。一个任务可能包括代码仓库、文件、数据库、容器镜像和验收脚本。多个带版本的任务组成 dataset。Terminal-Bench 是其中一套 benchmark；Harbor 负责把它运行起来。[任务与数据集版本机制]

因此，看到 Hub 上有很多 dataset，意味着可以获得更多工作场景；这些场景是否适合我们的模型能力、预算和目标，还需要筛选。

02 / 学习闭环

一次任务怎样变成一次强化学习？

例如让 Agent 修复一个订单服务：读取需求 → 检查代码 → 修改实现 → 运行测试 → 根据报错继续修改 → 提交结果。完整的一次尝试称为 episode / rollout；过程记录称为 trajectory；验收成绩称为 reward。

Harbor 任务环境任务、文件、终端或服务
↔
DSH Agent循环观察、决策、调用工具
↔
当前模型经 Gateway 生成下一步动作
↓ 执行完成：交付物、完整轨迹、任务与会话身份
Harbor Verifier检查真实结果并评分
→
训练连接层对齐 token、mask、reward 与模型版本
→
VERL 更新参数新模型进入下一轮尝试 ↺

这是目标接线示意；图中的 DSH × Harbor 训练连接尚未在本项目完成实跑验收。

  1. 尝试：同一任务可以采样多种解法，得到成功、失败和不同成本的轨迹。
  2. 验收：任务作者设计的 verifier 检查结果，例如业务测试是否通过。Harbor 负责调用它；评分的质量仍取决于验收标准。
  3. 训练：以 GRPO 类方法为例，比较多次尝试的奖励，形成更新信号；通常提高更好行为的概率。真实训练还包含长度、KL、mask 等约束，不能简化成“把成功答案背下来”。
  4. 复测：使用没有参与训练的任务，对比训练前后模型，确认提升能迁移到新工作。

Harbor 官方 RL 文档要求把 rollout 的 token 与奖励交给训练框架。可读日志有助于审计；训练还需要准确的 token IDs、参与损失计算的位置，以及后端所需的概率和版本信息。[官方 RL 接口说明]

同一次工作内

反思、重试、读记忆

改变当前决策所依据的上下文。模型参数可以完全不变，这也是有价值的 Agent 能力。

多次练习之间

训练、更新、重新评测

由优化器修改模型参数，希望改善以后遇到类似问题时的行为。是否有效要通过新任务验证。

03 / LONG-HORIZON

长流程训练，关键是把事情做完并做对

这里把 long-loop 理解为：一个目标需要多轮观察、工具操作、纠错和阶段交付，前面的行动会影响后面的工作。运行时间长只是现象；我们真正希望提升的是规划、恢复、记忆使用和最终完成率。

需要提升什么如何构造练习Harbor 能帮助什么
依赖顺序与规划先建立服务，再扩展功能，最后集成测试。共享环境中的有序步骤、阶段指令与验收。
错误恢复遇到测试失败、格式错误或服务异常后继续完成任务。可重置环境、固定故障场景、保留运行记录。
继承已有工作后一阶段必须使用前一阶段写出的文件或服务。步骤之间保留环境状态和产物。
可信完成与成本控制在同样时间、token 和工具预算下通过最终验收。验收结果、超时和产物记录；累计预算与训练资格还需连接层落实。

上述是面向本项目的任务设计建议。Harbor 的多步骤机制可以承载这类实验，但不会自动生成正确的教学顺序或奖励函数。

特别注意：环境连续，默认不等于对话连续。当前官方文档说明，多步骤任务共享环境，但每一步默认开始新对话；开启 --resume-trajectory 需要 Agent 原生支持会话恢复。接入 DSH 时必须验证其恢复能力，不能只加一个参数。[多步骤与会话恢复]

同一任务也可以只给一个总目标，让 Agent 自己完成几十次工具操作；这仍然是长流程任务。把步骤预先拆好，会帮助定位失败，也可能降低自主规划难度。建议同时保留“分阶段练习”和“只给总目标的最终考试”。

阶段奖励也需要设计。当前多步骤奖励默认取已执行步骤的平均值，也可使用最终结果策略；早停会影响聚合。我们应要求最终成果达标，避免“做完几个容易阶段”被误算成整个任务成功。[奖励聚合与早停]

开发者补充：为什么不能直接 cherry-pick #6444？

该实现不支持 partial rollout；策略版本字段有填零处理；多轮 token 前缀不一致时会分组选择；直接读取 Harbor reward，没有我们的 fresh receipt 审计。这些都需要对照当前 Gateway、VERL pin 和训练资格标准重新设计。关闭原因未获明确说明，不能推断为已合并迁移或技术否决。[AgentLoop 源码]

开发者补充：rLLM 能否直接整套嵌入？

rLLM 拥有自己的 Gateway 与训练循环，会和当前架构重叠。其 Harbor 示例开启 partial_rollout，而对应 VERL remote runtime 模式存在不支持组合。更适合先复用接线经验，整体替换应单独比较收益与迁移成本。[后端限制]

开发者补充：Tinker 教程的入口也需要按版本核实

Harbor Cookbook 的 tinker_rl 目录主要是指针；实际实现位于 tinker-cookbook。旧指针里的 launch_terminal_bench 命令与当前源码不同，应按实际 README 使用 scripts/train_terminal_bench.py。该路线需要 Tinker 服务访问权限，默认使用 Modal sandbox，不代表支持 Harbor 的全部原生 Agent、多步骤任务或 DSH。[实际入口] · [参数更新]

比较方案时先确认接入层级：复用 Harbor 任务格式、调用 Harbor 原生 Trial、训练 DSH Agent，是三个不同层次。一个层次可用，不能自动证明另外两个已经接通。

06 / 本项目接入提案

保留现有训练骨架，复用 Harbor 的环境与验收

本项目要证明的是 DSH 驱动的 Agent 经训练后更会工作。训练 Harbor 内置 Terminus-2 可以验证基础设施；DSH 的工具、记忆、循环和停止行为仍需自己的验证。

  1. 先验证一个小任务的环境与验收。

    选明确不需要 GPU 的单容器任务，运行 oracle 参考解，确认环境能启动、评分能生成、产物可检查。Oracle 是任务作者提供的解法，不代表模型已经解出任务。

  2. 让 DSH 在这个环境里真正工作。

    按 Harbor 自定义 Agent 接口适配 DSH 生命周期、工具访问和停止行为。模型请求通过现有 Uni-Agent Gateway；检查容器能否访问 endpoint，以及 artifact 是否来自本次运行。[自定义 Agent 教程]

  3. 把轨迹、评分与训练资格对齐。

    以 task / trial / session 为关联键，绑定真实 token、模型版本、最终验收和新鲜回执。基础设施失败、数据缺失和正常任务失败要分开处理，不能统一伪装为有效零分样本。

  4. 做最小训练与独立复测。

    真实调用 VERL 更新参数，保存并重新加载 checkpoint，再用冻结的未见任务与相同预算比较 base 和 trained。先验证训练闭环与结果可信，再增加任务数量和流程长度。

连接层需要约定的接口

以下是设计要求，不代表已经添加了同名 API 或字段。

边界必须传递 / 验证
任务 → Harbor固定 task 版本、环境身份、输入、资源与时间预算；任务可独立重建。
Harbor → DSHinstruction、环境执行能力、模型 endpoint、会话上下文、超时与完成状态。
Gateway → 训练prompt / response token IDs、有效 response mask、后端所需 logprobs、策略版本、trial/session 关联。
Verifier → 准入审计reward、异常类型、产物身份；保留 DSH 新鲜回执与资格检查，拒绝错配和重放。
VERL → 验收真实 optimizer update、checkpoint 可独立加载、未见任务的同预算对比结果。

实现时预计涉及的范围

已有 uni_agent/tasks/harbor/task.py、reward.py 和 preprocess.py 是复用起点。需评估新增 Harbor-compatible DSH Agent 适配、训练配置与真实联调测试；准确文件清单和版本锁定应在实现设计中确认。本专题只新增文档与交接链接。

现有 HarborTask 将 agent 名称交给 Harbor CLI，绕过 Uni-Agent Agent registry；因此填入 agent.name: dsh 不会自动加载我们的 DshAgent。当前 --dsh-strict-audit 也限定 dsh_architecture，需新增 bridge 并适配审计合同。见 当前 Task 实现 与 推理入口。

验证顺序：任务与 oracle → DSH 生命周期 / timeout → Gateway token 与 trial 对齐 → fresh reward 与失败分类 → 一次真实参数更新 → checkpoint reload → sealed holdout。CPU 合同测试和真实运行证据分别记录。

07 / 入门教程

从一个能看懂的任务开始

建议依次阅读和实践以下内容。入门命令仅供理解，本文档生成时没有安装 Harbor、执行任务或调用付费模型。

  1. 认识任务、Agent 和评分。

    读 官方入门概览，再看 Cookbook 的 simple-task。先看它要求什么、环境有什么、tests 如何判定成功。

  2. 使用 oracle 了解一次运行的全过程。

    你提供的 Terminal-Bench 教程要求先安装并运行 Docker，然后使用 oracle 验证环境。它展示的是 benchmark 运行流程。

  3. 再用真实 Agent 完成同一任务。

    比较 oracle 与 Agent 的日志、产物和评分；理解模型为什么失败。可查看 Agent 接入教程，随后再接我们的 DSH。

  4. 学习长流程任务的组织方式。

    读 Multi-step Tasks，设计两个或三个有依赖关系的步骤。分别测试环境状态延续、会话恢复和最终成功条件。

  5. 最后理解训练连接层。

    读 Harbor RL 工作流 与 Tinker RL 示例，把“生成轨迹”和“更新模型”两段代码对照起来。

首次实践：运行一个已确认的 CPU 任务

# 先准备并启动 Docker；以下是使用示意，没有在本项目执行。
uv tool install harbor

# 将占位路径换成已准备好的单个 CPU 任务目录，且该任务须提供 oracle 解法。
harbor run -p /path/to/cpu-task -a oracle

-p 本地任务用法来自官方 Cookbook；oracle 用法见 Terminal-Bench 教程。这里的组合是单任务入门建议，具体任务尚未选定或实跑。

官方 Terminal-Bench 完整数据集命令（并非单任务首跑）

官方教程使用下列命令运行整个数据集的 oracle 解法；这会启动多个任务，应先了解资源需求：harbor run -d terminal-bench/terminal-bench-2 -a oracle。

你提供的 Hub latest 与旧教程指向不同任务集。本次访问 terminal-bench/terminal-bench/latest，显示 revision 4 / 4.0.0、66 个任务，并明确包含 GPU 与多容器任务。小规模入门应先选单个 CPU 任务；实验时固定 revision / digest，避免 latest 变化让两次成绩不可比。

多容器、MCP、模拟用户、技能和计算机操作的进一步教程集中在 官方 Cookbook。无需一开始就把所有能力都接入。

全局目标：证明 Qwen3-4B 在固定 DSH / Uni-Agent / VERL 条件下训练后，对未见任务的完成能力优于 frozen base；进一步验证长流程、隔离和可复用工作方式。

短期建议：继续恢复可复建 Linux / DSH runtime，完成现有八类真实 smoke；同时把一个 CPU Harbor 任务作为独立环境与验收验证点。待版本、接线与成本明确后，再决定是否把训练任务迁入 Harbor。

不需要为了阅读教程或生成这份专题先租 GPU。简单 CPU 任务与 oracle 可先验证 Harbor。真实模型推理可用 API 或自托管模型；本项目固定 Gateway / VERL 链路的实跑与权重训练要单独准备算力。Hub 中某些任务本身也需要 GPU，因此资源需求必须按任务和训练方案判断。

具体状态与现有 GPU 前置条件以 本 worktree 进度、运行手册 和 历史目标账本 为准。这份专题不改变既有 smoke 或训练资格。

为什么不能直接拿 benchmark 反复训练，再报更高成绩？

这样容易把对训练题目的熟悉误认为通用能力提升。可以使用 Harbor 格式的任务训练，但应分开训练集与封存评测集，并冻结版本、预算和 verifier。最终关心的是模型在新任务上是否更可靠。

Harbor 会自动让 Agent 学会记忆、规划和自我进化吗？

它提供承载和测量这些能力的任务环境。具体学什么取决于任务分布、Agent 的可用操作、奖励以及训练算法。修改提示词、技能和记忆机制也能提升表现，但应单独归因，避免与模型参数更新混淆。
