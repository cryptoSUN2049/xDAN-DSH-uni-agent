02 / 我们究竟要证明什么

让 Agent 在未见任务上更可靠地完成工作

第一阶段：模型能力学习

固定 DSH Harness，让 Qwen3-4B 经 Uni-Agent + VERL 训练，改善工具使用、任务组合、诊断恢复和资源清理。

第二阶段：受控 Harness 进化

提出有版本的工作方式或插件候选，在独立任务上比较收益；通过验证后再进行小范围试用、晋升和回滚演练。

验收比较必须固定任务版本、预算、模型输入约定和 verifier。当前规划的 P5 使用 32 条封存 paired holdout，判断训练收益及不确定性；不是只看训练集 reward 上升。P6 再验证候选复用与隔离。[原目标与历史资格]

Harbor 是任务与验收底座，Modal 是执行环境供应方。两者帮助我们把训练和比较做得可重复，不自动证明模型或 Harness 已经进步。

04 / 代码事实

Modal 已有适配；两条环境路径不能叠加

A. 原生 Task 路线

Uni-Agent Task → Uni-Agent Sandbox(provider=modal 等) → Agent
现有 DSH Task 创建 Uni-Agent sandbox，再在其中执行 DSH helper。

代码起点：DSH Task、DshAgent、Uni-Agent ModalSandbox。有 provider 代码，不等于当前严格 v3 路线已经在 Modal 上实跑。

B. Harbor Task 路线

Uni-Agent HarborTask → Harbor CLI / Trial → Harbor Modal Environment → Agent

HarborTaskConfig明确使用 sandbox: None；harbor_env 会传给 Harbor 的 --env。已有的 oracle 配置是：

# 已有配置：评估用；本次未执行。
- name: harbor
  agent:
    name: oracle
  harbor_env: modal
  timeout_multiplier: 1.0
Harbor 路线不要再设置 Uni-Agent sandbox.provider: modal。让 Harbor 管理该任务的环境；否则容易重复创建沙箱、弄错工作目录和清理责任。若有意启用独立 verifier 沙箱，那是明确的评分隔离设计，不属于重复包装。

Modal 的官方示例确认，harbor run --env modal 由 Harbor 创建 Modal 沙箱。示例验证的是 oracle eval，不能据此认定 DSH RL 已通过。[官方集成示例]

05 / 集成设计

新增薄的 DSH bridge，保留一个环境所有者

  1. Harbor 创建环境。固定任务版本，准备包含可复建 DSH Linux runtime 的镜像。用 Docker 做低成本首验，随后对同一任务验证 Modal。
  2. Bridge 在该环境中执行 DSH。把 Harbor Environment 的命令与文件操作映射给 DSH runner，提供工作目录和任务指令；bridge 不再次调用 Modal 创建 API，也不自行销毁 Harbor 持有的环境。
  3. 模型请求仍走 Uni-Agent Gateway。保留实际 session 路由、token 与模型版本；不能把普通模型 API 伪装成训练 Gateway。
  4. 验收结果进入统一证据合同。保留 task / trial / Gateway session / rollout index 的关联，验证 DSH trace、artifact 和 fresh receipt，再决定训练资格。
  5. 训练闭环单独验证。经过准入与 TransferQueue 读回后，再做 VERL update、checkpoint reload 和 paired holdout。
关键连接当前事实必须补齐
DSH Agent 注册HarborTask 将 agent 名称直接传给 Harbor，绕过 Uni-Agent registry。真正的 Harbor-compatible DSH adapter；只填 agent.name: dsh 不会自动加载 DshAgent。
Gateway 网络当前适配注入 endpoint / key，没有自动建立 Harbor → Gateway 隧道。从 DSH 所在 Modal 环境验证带认证的实际 Gateway endpoint；localhost 指向沙箱自身。
任务与运行包Harbor task_path 是执行 worker 可见的本地路径。worker 分发固定任务包；DSH runtime、fixture 与产物路径分别核验，不能假设开发机路径存在于云端。
评分与资格本仓 Harbor → TaskResult 适配返回 reward / accuracy，finished=None；尚未映射 DSH 的 verifier_reward / reward_info 与完整 lineage。把可信验收转为可审计结果，区分有效失败、基础设施故障、缺失或重放证据；这是当前适配缺口，不是 Harbor 框架的结果字段上限。
严格 v3 CLIdsh-strict-audit 限定 dsh_architecture；当前 episode staging 限定 local。评估独立的 Harbor bridge 验证路径及严格审计适配，不能直接切 provider 冒充已验收。

部署位置与凭据

推荐在受控 worker / 控制端保留 Modal 管理凭据，由它启动 Harbor。Agent 环境只获得完成任务所需的访问能力及受限模型会话。Gateway 的跨主机访问方式必须先验证；本方案不预设公开暴露端口，也不假定现有 localhost URL 可直接复用。

模型 GPU 与 Modal CPU 沙箱是不同资源。先验证连接再决定推理 / 训练部署地点，不要求同时购买两套 GPU。Modal 云端任务同样涉及资源使用，本文只提供设计，没有创建或调用。

接入合同（拟议，非现成 API）

输入输出与约束
task revision、trial ID、instruction、已有 EnvironmentDSH 仅在指定环境工作，记录 runtime 身份与结果。

06 / 三个不同的循环

长流程负责把工作做完，训练负责改善下一次工作

任务内的 long loop

观察 → 决策 → 工具 → 反馈 → 继续。Harbor 多步骤共享环境；默认不共享对话，恢复会话需要 Agent 原生支持。

任务之间的 RL loop

多个任务生成经历 → 累积合格训练批次 → VERL 更新模型 → 再做任务。全异步让执行与训练分别推进，减少等待慢任务。

更外层的 Harness / RSI loop

固定评测与预算
  → 提出 Harness candidate
  → 在独立 Harbor 任务中执行
  → 对比基线、验证复用和边界
  → 小范围试用 / promotion / rollback
  → 下一轮候选

Harbor 适合提供这一循环的任务和实验条件；候选生成、晋升与回滚控制器仍由我们的系统实现。Harbor 已有 GEPA 优化 Harness 的公开例子，但这不等于本项目 P6 已完成。先分别验证模型学习与 Harness 改进，再联合优化。[官方优化示例] · [会话恢复] · [全异步训练]

07 / 执行次序与验收

先验证一条链，再扩大规模

里程碑动作通过证据
H0 环境选单个 CPU 任务，Docker oracle；随后同任务 Modal oracle。任务版本一致、结果可复查、artifact 可读取、环境正确结束。
H1 DSH 接入Bridge 复用 Harbor 环境运行 DSH，通过实际 Gateway 完成任务。真实进程、模型请求、任务结果与 session 对应；验证 timeout / cancel。
H2 严格合同绑定 token、trace、fresh receipt 和训练资格。错配、重放、缺失、篡改必须被拒绝；正常策略失败不能与基础设施故障混淆。
H3 最小训练固定模型与版本，形成合格批次并真实更新。trainer 消费证据、参数变化、checkpoint 独立 reload。
H4 能力与扩展paired holdout；再扩任务数、长度与异步并发。同预算下的未见任务收益；随后单独验收 Harness 进化。

这是新增 Harbor 路线的设计编号，不替代原有 M1 / P0–P6。现有八类 DSH smoke 继续作为独立验收点，不因引入 Harbor 而重写已验证执行器。

预计改动范围

  • 新增 Harbor-compatible DSH Agent bridge 与非拥有型环境适配；具体文件命名在实现前锁定。
  • 按需复用 DSH runner；审查 Harbor Task / reward 与现有 DSH 证据合同的接口。
  • 新增单任务 recipe、镜像 / 版本清单、环境与网络预检、bridge 单元测试和有界 live 集成测试。
  • 保留固定 VERL 483b8a009ba3a97563edee3a19887e4862b8094a；升级或整体换用 rLLM / Tinker 要另做兼容与成本比较。

本轮已授权的是方案核查和文档交付；未实现 bridge、未部署 Modal、未启动模型或 GPU。实现前需完成版本锁定与具体接口设计，按项目 Development Preflight 呈现后取得明确实现批准。
